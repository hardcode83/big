## Implementation Notes

- `frontend/node_modules` was missing at session start (`npm install` run first, 606 packages) — pre-existing environment gap, unrelated to this change; no action beyond installing.
- 1.1: both permissions added `TENANT_OWNER`-only; test file extended with a loop-based case per permission across all five roles plus the two unauthenticated-user cases (35 tests total, up from 25).
- 1.3 `dto.ts` exact names: `UserDto`, `UserListDto` (`{data, total, page, perPage, totalPages}` — the older `{data,...}` envelope, not `{items,...}`), `CreatedUserDto` (`{user, temporaryPassword}`), `TenantConfigDto`, `TenantDto`, `CreateUserInput`, `UpdateUserInput`, `UpdateTenantInput`. Also exported (not explicitly named by 1.3 but needed by callers): `UserRole`, `UserStatus`, `TenantStatus`, `StorageType` (re-exported from generated OpenAPI), and `UpdateTenantConfigInput` (the nested partial-config type `UpdateTenantInput.config` uses, mirroring `TenantConfigPatch`).
- `UserDto` carries no `tenantId` field — `UserResponse` (unlike `PlatformUserResponse`) has none; tenant scoping is implicit in the bearer token per `user-management` §Aislamiento.
- `TenantConfigDto.storageType` is typed as the narrow `StorageType` union (`"LOCAL" | "S3"`), not a generic `string` like `features/platform/dto.ts`'s equivalent field — more precise and harmless since `storage_type` is read-only here (no patch control, confirmed absent from `TenantConfigPatch`).
- `UpdateTenantConfigInput.ownerApprovalThresholdEur`/`aiConfidenceThreshold` are typed `string | number | null` (matching `TenantConfigPatch`'s own wire type), unlike `TenantConfigDto`'s read-side `string`. This is the first input-side `Numeric` field in the codebase per design.md's callout; the convention (send the exact decimal-precision string) is documented in a `dto.ts` comment for section 4's form to follow.
- 1.4 `HttpTenantSettingsSource` gives every `/api/v1/users*` method an explicit unused `_tenantId: string` first parameter, mirroring `HttpReservationsSource` (tenant scoping stays honest even though these routes carry no `tenant_id` path param). `getTenant`/`updateTenant` use `tenantId` for real — it is a genuine path parameter on `/api/v1/tenants/{tenant_id}`.
- `listUsers` always sends `page`/`per_page` (defaulted 1/20) and only adds `role`/`status` to the query when the caller passes them — needed as-is by design D8's `use-active-cleaner-count` (`role=CLEANER&status=ACTIVE&per_page=1`) in section 2.
- `updateUser`/`updateTenant` (incl. nested `config`) send only the keys present on the input object (`!== undefined` spread pattern), mirroring `http-incidents-source.ts`'s `triageIncident`. `deactivateUser` maps `DELETE /api/v1/users/{user_id}` (design D7), returns `void`, no response body to map.
- No blockers or design conflicts encountered; all eight endpoint mappings matched the `openapi.d.ts` schemas/paths without ambiguity.
- 2.1 `tenantSettingsKeys` (`hooks/query-keys.ts`): `usersList(tenantId, filters?)`, `userDetail(tenantId, userId)`, `tenantDetail(tenantId)`, `activeCleanerCount(tenantId, role, status)` — all on `tenantScopedKey`. `filters` on `usersList` defaults to `{}`; every mutation invalidates with `usersList(tenantId)` (no filters arg) — TanStack v5's `partialMatchKey` treats a trailing `{}` as matching any object at that position, so this invalidates every cached filter/page combination in one call, exactly D7's quoted shape.
- 2.2 `useUsers(filters?: UserFilters)` and `useUser(userId: string)` (both `hooks/use-users.ts` / `use-user.ts`), each with its own **non-exported** local `useTenantId()` — duplicated per file, not shared, mirroring `use-reservations.ts` + `use-guest-access-token.ts`'s precedent of not centralizing it. `UserFilters` is imported from `../data/http/http-tenant-settings-source` (section 1 left it there, not in `dto.ts`; section 1 files were not touched).
- 2.3 `useCreateUser(): UseMutationResult<CreatedUserDto, Error, CreateUserInput>` and `useResetPassword(): UseMutationResult<CreatedUserDto, Error, string>` (variable is the `userId`) — both `gcTime: 0`, both invalidate `tenantSettingsKeys.usersList(tenantId)` `onSuccess`. Neither takes `tenantId` as a hook argument (unlike `useCreatePlatformUser(tenantId)`); it comes from `useTenantId()` since the acting user is always scoped to their own tenant here.
- 2.4 `useUpdateUser(): UseMutationResult<UserDto, Error, {userId: string; input: UpdateUserInput}>` (note: variables object, not two positional args) and `useDeactivateUser(): UseMutationResult<void, Error, string>` (variable is the `userId`) — both invalidate `usersList(tenantId)` and `userDetail(tenantId, userId)` `onSuccess`. Reactivation is `useUpdateUser().mutate({userId, input: {status: "ACTIVE"}})`, no separate hook (D7).
- 2.5 `useActiveCleanerCount(enabled: boolean): UseQueryResult<number>` — `enabled` has **no default**, callers must pass it explicitly; `data` IS the `total` (not `data.total`) via the `queryFn`'s own `.total` extraction from `listUsers`'s `UserListDto`.
- 2.6 `useTenant(): UseQueryResult<TenantDto>` (no args, tenant id from `useTenantId()`) and `useUpdateTenant(): UseMutationResult<TenantDto, Error, UpdateTenantInput>`, invalidating `tenantSettingsKeys.tenantDetail(tenantId)` `onSuccess`.

- Gotcha (naming mismatch, both sides intentional): `validateTenantConfig`'s errors are keyed camelCase (its own DTO-shaped naming); `mapFieldErrors`'s errors are keyed by whatever `loc`'s last segment names on the wire — the backend's snake_case request-body field (e.g. `owner_approval_threshold_eur`), unaffected by the field living inside the nested `config` object in the request. The form's `errorFor(clientKey, backendKey)` helper reads both by their own two names rather than assuming one shared key; every inline error site passes both explicitly (e.g. `errorFor("ownerApprovalThresholdEur", "owner_approval_threshold_eur")`).
- Gotcha (TypeScript): the internal `diff<T extends object>(current, base, fields)` helper returns `Partial<T>` inferred from `values`/`baseline` (both `EditableValues`, all fields non-nullable) — kept in that narrower shape (not cast to `UpdateTenantInput`/`UpdateTenantConfigInput`, whose fields are wider unions including `null`) so `validationInput` extraction and the post-success `setBaseline` merge never have to think about `null`; the narrower shape widens implicitly (no cast) only at the two call sites that actually build the API payload (`{...tenantChanges}`, `input.config = configChanges`).
- The Numeric-field convention (dto.ts's comment) is honored literally: `ownerApprovalThresholdEur`/`aiConfidenceThreshold` are plain `<input type="text" inputMode="decimal">`, state typed `string`, sent as the exact string the user typed (never round-tripped through `Number()`), confirmed by a dedicated test.
