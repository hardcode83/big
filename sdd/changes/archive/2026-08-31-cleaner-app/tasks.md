## 3. Lib helpers — actions table, conflict reasons, error mapping, format

- [x] 3.1 Create `frontend/features/cleaner/lib/cleaner-actions.ts` exporting `type CleanerAction`, `CLEANER_ACTIONS: Record<CleaningTaskStatus, readonly CleanerAction[]>`, and `NO_ACTION_REASON: Record<CleaningTaskStatus, string>`. The `Record` must be exhaustive (design D6): `ASSIGNED → [accept, reject]`, `ACCEPTED → [start]`, `IN_PROGRESS → [complete, reportIncident]`, `PENDING_REVIEW → []`, `COMPLETED → []`, `REJECTED → []`, `CANCELLED → []`, `CREATED → []`, `FAILED → []`. Reading an unknown status returns `[]` via `Object.hasOwn`, never `undefined`. [R3.1, R8.4]
- [x] 3.2 Create `frontend/features/cleaner/lib/conflict-reason.ts` exporting `ConflictReason` (`"missing-required-items" | "missing-required-photos" | "critical-incident"`) and `conflictReason(task: CleaningTask): ConflictReason`. Reads the refreshed task after invalidation (design D7): `pendingChecklistRequiredItems` non-empty → `missing-required-items`; `pendingPhotoRequiredTypes` non-empty → `missing-required-photos`; otherwise `critical-incident`. The source of truth is the backend; the helper only maps the post-refresh state to a reason key. [R7.3]

The function never returns the raw envelope message (design D12, R7.3). [R5.5, R6.5, R7.3, R8.2]
