## 2. Listener de expiración (D2, D5) <!-- hard --> <!-- panel: PASS 2026-09-04 -->

> **Por qué `hard`:** el cuerpo del listener detecta la carrera de R3 (login gana al refresh viejo) con una guarda basada en `getSessionTokens()`; la decisión D5 (D5.1-3) tiene varianza real porque hay tres alternativas rechazadas en el design que diferencian el comportamiento (capturar vs no capturar, comparar generaciones vs null-check de tokens, ignorar la mitad del comentario de "contrapartida aceptada"). - Third panel fix round (post third `/sdd:review`, sdd-security FAIL — architect also FAILed on doc-drift from round 2, fixed separately as D7 in `design.md`/`proposal.md`; this round's fix is tracked as R6 in `proposal.md` and D8 in `design.md`). This round's security finding was categorically different: not a missed call site but a soundness gap in D5 itself. The app has 11 independent `createAuthenticatedClients()` instances (one per feature module — verified via `grep -rl createAuthenticatedClients`), all sharing the single module-level `inFlight` singleton in `refresh-coordinator.ts`. D1 made `purgeSessionCache()` advance `sessionGeneration` for a purely cache-invalidation reason, unrelated to token identity — but `refresh-coordinator.ts`'s guard and D5's listener both still (mis)used that same counter as a proxy for "did the session's identity change". Reachable interleaving (traced and reproduced in tests): a refresh under session A is in flight; `login()` installs session B and purges (advancing the shared counter); a genuinely separate, concurrent refresh for session B (triggered by a different feature client's 401) is also in flight, captured at the post-login generation; when session A's stale refresh settles and the listener purges again, the shared counter moves again — even though nothing about session B's identity changed. When B's own refresh then settles: if it succeeds, the coordinator wrongly discards a validly-rotated token pair (`SessionInvalidatedError`, thrown solely because of an unrelated purge); if it fails (genuinely revoked/expired), the coordinator wrongly skips clearing, and the listener's `getSessionTokens() !== null` check also skips cleanup — a genuinely-dead session gets stuck "authenticated" forever. The pre-change listener was fail-closed here (unconditional clear); this one is fail-open. Fix: split the single counter into two — `sessionGeneration` (unchanged: cache-invalidation, moves on every `purgeSessionCache()`/`setSessionTokens()`, used by `use-mark-read.ts`/`use-mark-all-read.ts`, R1/R4.4) and a new `tokenGeneration` (identity: moves ONLY on `setSessionTokens()`/`clearSessionTokens()`, never on a bare purge). `refresh-coordinator.ts` now captures/compares `getTokenGeneration()` instead of `getSessionGeneration()` — added to `session-store.ts` with a module-doc explaining the split and why it exists. The listener in `auth-provider.tsx` needed no logic change (its `getSessionTokens() !== null` check becomes sound once the upstream signal is), but its comment and `login()` catch's comment were updated for accuracy (the resurrection guard from round 2 now comes structurally from `clearSessionTokens()` bumping `tokenGeneration`, not from the `purgeSessionCache()` call, which stays for cache hygiene only). Also fixed finding 3 (lower severity, same root cause): `refresh-coordinator.ts`'s own guarded clear now calls `purgeSessionCache()` before `clearSessionTokens()`/`clearSessionPresent()`, so cache invalidation and the token clear stay coupled at that site too instead of depending on every future caller of `refreshSession()` to purge afterward on its own.
