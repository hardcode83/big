## Implementation Notes

### Section 1 (backend: `classify_by_triage`)

- `Incident.set_triage(*, now, category=None, severity=None, estimated_cost=None) -> bool` — returns `True` only when this call classified the incident; parameters unchanged.
- New transitions row is keyed `"classify_by_triage"` (`OPEN` → `CLASSIFIED`); `classify` untouched.
- `PATCH /api/v1/incidents/{incident_id}` now answers `200` with `status: "CLASSIFIED"` when the body carries **both** `category` and `severity` and the incident was `OPEN`; with only one of them (or only `estimated_cost`) it still answers `200` with `status: "OPEN"`. The frontend must re-read `status` from the response of every triage, not assume it is unchanged.
- Same call with an `estimated_cost` above the tenant threshold answers `status: "AWAITING_OWNER_APPROVAL"` (it passes through `CLASSIFIED`), so a triage can move the incident two steps in one request.
- Request schema unchanged (`TriageIncidentRequest`, `extra="forbid"`, the three fields optional, `estimated_cost` as a decimal string): the only contract change is the route `description`, so `frontend/lib/api/generated/openapi.d.ts` regenerated with **no type change** — section 2 needs no new generated types for `triageIncident`.
- `backend/openapi.json` and `frontend/lib/api/generated/openapi.d.ts` are regenerated and left uncommitted in the working tree.
- `POST /incidents/{id}/classify` is still needed as a separate action: the automatic classifier is the only path that writes `ai_classification`/`ai_summary`, and `set_triage` never touches them.
- Audit stays a single `INCIDENT_TRIAGED` row whose `changes.status` is always present (`old == new` when nothing moved); no second `INCIDENT_CLASSIFIED` audit row. The timeline gains `INCIDENT_CLASSIFIED` with `actor_type = USER` only when the triage classified.
- Property state recomputes only on that transition: `HIGH` → `INCIDENT_HIGH`, `CRITICAL` → `INCIDENT_CRITICAL`, `MEDIUM`/`LOW` → nothing. A triage that does not classify never moves the property, whatever the severity.
- Test-side gotcha for anyone extending `backend/tests/maintenance/test_entities.py`: `classify_by_triage` is excluded from `_REJECTED_CASES` via `_ANNOTATES_INSTEAD_OF_REFUSING` (it annotates instead of raising outside `OPEN`), and `Operation` is now `Callable[[Incident], object]`.
- Cross-tenant `PATCH` asserts only the `404`: the shared test session is bound to the caller's tenant, so reading the neighbour's row back returns `None` either way.
- Panel PASS 2026-09-05 (architect, security, i18n, tenancy: PASS; qa: FAIL then reviewed by the orchestrator). QA's finding — "triaging `estimated_cost` alone, above the tenant threshold, on an `OPEN` incident raises `InvalidIncidentTransitionError` → `409` instead of leaving the incident cleanly `OPEN`" — is real but **pre-existing**, not introduced by this section: `TriageIncidentUseCase.execute` called `needs_owner_approval`/`require_owner_approval` unconditionally (independent of `category`/`severity`) before this change too, and the same 409 already fired on that combination. Design D3 names this exact effect explicitly ("Si trae sólo el coste, sigue dando `409` exactamente como hoy") and rejects reordering; its mitigation is D9 (a dedicated `conflictReason` message for `triage` on `OPEN`, in section 4/frontend), not a backend change. Finding dismissed for section 1 with this rationale; section 4 must implement D9's `triage`-on-`OPEN` message or R1/R6.1 in that section will be incomplete.
