- Section 1 (2026-09-13): `render_checkin_reminder_email(language, property_name, check_in_date: date, check_in_time_local: time) -> tuple[str, str]` lives in new `backend/app/reservations/domain/notifications.py`. Section 2 adds `render_checkout_reminder_email(...)` to the **same file** (design D6) — keep the `_CHECKIN_SUBJECT`/`_CHECKIN_BODY` dicts as-is and add sibling `_CHECKOUT_*` dicts, don't rename anything.
- `SendCheckinRemindersUseCase` (`reservations/application/use_cases.py`) ports: `properties: PropertyRepository`, `reservations: ReservationRepository`, `guests: GuestRepository`, `notifications: NotificationLogRepository`, `uow: UnitOfWork`. `execute(*, tenant_id, now) -> CheckinReminderReport` (fields: `candidates`, `written`, `skipped_missing_email`, `skipped_invalid_local_time`).
- Candidate query: loads `properties.list_all(tenant_id)` first, then `reservations.list_for_properties(tenant_id, property_ids, today-1, today+1)` (module constant `_CANDIDATE_WINDOW = timedelta(days=1)`) — **no new repository method was added**; `list_for_properties`'s stay-overlap semantics are deliberately over-inclusive, and the precise `effective_bounds` + threshold check in Python is what actually decides (design D3/D4). `CONFIRMED` status is filtered in the Python loop, not in SQL (mirrors `list_for_properties`'s own "no status filter" precedent). Reuse this same shape for `SendCheckoutRemindersUseCase`'s candidate query (swap the threshold to `checkout_instant`).
- Recipient resolution is a private `_recipient(tenant_id, guest_id) -> tuple[str, str] | None` method (email, `preferred_language`), mirroring `SendGuestAccessTokenUseCase._recipient` but returning `None` instead of raising. Reusable as-is for the checkout use case (same guest, same reservation shape).
- **Gotcha, AST census (`test_writer_census.py`)**: `NotificationLog(...)` must be built with a **literal** `notification_type=NotificationType.<X>.value` at the call site — a loop variable holding the enum member is invisible to the census (measured: it silently dropped both new types from `WITH_WRITER`). Solved here with a private `_write_if_new(...)` helper that has one `if/elif` branch per `NotificationType` member, each with its own literal `NotificationLog(...)` construction. Section 2's `CHECKOUT_REMINDER` writer needs the same shape (either add a third branch here or a parallel helper — either way, the literal must appear textually per type).
- **Gotcha, second AST guard not mentioned in tasks.md**: `tests/notifications/test_channel_literals.py` allowlists every file that references `NotificationChannel.<X>` as a bare literal (D6 of `notification-channel-routing`). Since design D12 has each writer target `NotificationChannel.EMAIL` directly (no `resolve_channels`/`dispatch_channels`), `app/reservations/application/use_cases.py` had to be added to `CHANNEL_LITERAL_WHITELIST` in that test file (both the set and its `test_whitelist_is_exactly_the_design_d6_set` pin) — cited to this change's own design D12. Section 2 does not need a second entry (same file, already whitelisted); section 3's `access/application/use_cases.py` will need its own entry there.
- `effective_bounds(property, reservation)` raises `IncompatibleTransitionContextError` (from `app.properties.domain.exceptions`) — caught per-candidate, counted in `skipped_invalid_local_time`, sweep continues.
- `check_in_time_local` passed to the renderer is `reservation.check_in_time or property.default_check_in_time` — a plain fallback expression written directly in the use case (not a call into `ContextualStateResolver`'s private DST arithmetic, which stays untouched).
