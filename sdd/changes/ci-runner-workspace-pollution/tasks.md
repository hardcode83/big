- **3.1-3.3, `infra/environments/dev/runner-job-started.sh`**: read `runner-bootstrap.sh` in full before writing anything — confirmed the layout it assumes: per-agent user `actions-runner-<i>`, home `/opt/actions-runner-<i>`, group `ci-agents` with `%ci-agents ALL=(ALL) NOPASSWD:ALL` in `/etc/sudoers.d/91-actions-runner-pool` (bootstrap §"Grupo + sudoers", installed unconditionally for the pool). The hook's `chown -R` goes through `sudo -n` (not bare `sudo`): `-n` costs nothing in real usage (already passwordless via that sudoers grant) but makes a mis-provisioned host fail fast into the R3.5 branch instead of hanging — GitHub's docs state there is no timeout for job-started hooks, so a `sudo` prompt nobody can answer would hang the job indefinitely rather than fail it.
  - **Override mechanism (exact name)**: an optional first positional argument, `WORK_DIR_OVERRIDE` (e.g. `runner-job-started.sh /tmp/some/_work`). No arguments → self-locates `$RUNNER_HOME` as two directories up from the script's own resolved path (`$(dirname "$(dirname "<resolved script path>")")`) and targets `$RUNNER_HOME/_work`. Verified against the real installed layout (`$RUNNER_HOME/hooks/runner-job-started.sh` → `$RUNNER_HOME/_work`) with a synthetic `actions-runner-7/hooks/…` tree.
  - **Validation-failure exit code: 0, not non-zero.** The "no actúa" (does not act) behavior follows task 3.1's own description ("...; si la validación falla, no actúa") together with R3.6 ("THE SYSTEM SHALL acotar la actuación del hook al `_work/` del agente que lo ejecuta, y NOT actuar sobre el de otro agente ni sobre rutas fuera de él" — the closest EARS requirement in spirit to "don't act on an unrecognized/invalid path"), NOT R3.1's own EARS text: R3.1 is only "THE SYSTEM SHALL versionar en el repositorio un script de hook de inicio de job, bajo `infra/environments/dev/`" — purely about versioning the file, silent on validation-failure behavior. (Fix round, see below: this misattribution was flagged by the review panel and corrected here and in the script's header comment.) GitHub's `bash -e <path>` invocation means a non-zero exit fails the whole job, and a validator being wrong about an edge-case path should not fail a real job whose checkout would otherwise have succeeded. Verified this holds even under GitHub's actual invocation contract, not just this repo's unflagged test harness: ran `bash -e runner-job-started.sh relative/_work` and `bash -e runner-job-started.sh <clean tmp _work>` directly (via `subprocess`, `-e` set exactly as GitHub sets it) — both exit 0. This works because every fallible test in the script is inside an `if`/`elif` condition or an explicit `|| true`, never a bare statement `-e` could trip — the script's own `set -uo pipefail` (not `-e`) documents that the *script* doesn't rely on `-e` either way, but the protected-context pattern is what actually makes it safe under the externally-imposed `-e`.
  - A genuine `chown` failure (validated path, but the privileged step itself fails) exits non-zero and names `$RUNNER_HOME` explicitly (derived as `dirname "$WORK_DIR"`, which after validation is guaranteed to be `$RUNNER_HOME` whether self-located or overridden) — per R3.5.
- **3.4, `infra/environments/dev/test_runner_job_started.py`** (pytest, not `.sh` — matches this repo's uniform `scripts/test_*.py` convention, which the task text explicitly allows as "equivalente ejecutable desde la suite del repo"). Drives the real bash script via `subprocess.run`, never imports or mocks it. 8 tests:
  - `test_clean_tree_needs_no_action` — genuine, no stubs: exit 0, before/after `(uid, mode, mtime_ns)` snapshot of every entry identical.
  - `test_relative_path_does_not_act` / `test_nonexistent_path_does_not_act` / `test_path_not_ending_in_work_does_not_act` — genuine, no stubs: exit 0, message explains why, target tree (where one exists) untouched.
  - `test_detected_and_chown_succeeds` / `test_chown_genuinely_fails_names_runner_home` — **privileged-fixture limitation**: a genuinely foreign-owned (e.g. root-owned) fixture file cannot be constructed by an unprivileged test process (chowning a file to a *different* owner requires privilege this sandbox does not have). Per the task's own guidance, these two stub the external `find`/`sudo` commands via a `PATH`-prepended directory (never mocking the script itself) — `find` unconditionally reports one fake foreign path to force the script's "something to do" branch, and `sudo` is a script that ignores its arguments and exits 0 or 1 to pin the chown outcome deterministically. This exercises the real control flow (detection log line, chown invocation, success/failure logging, exit code, `$RUNNER_HOME` naming) honestly but not a genuine permission failure/success — running that requires a host where the test process can create real root-owned files (root in a container, or real passwordless sudo), which this sandbox lacks. Documented in the test module's own docstring, not silently mocked.
  - `test_chown_genuinely_fails_without_stubs_when_sudo_has_no_password` — a bonus, *mostly*-unstubbed variant: only `find` is stubbed (to force the branch); the real `sudo -n` on `PATH` is left alone. In this sandbox, verified during implementation that `sudo -n true` exits 1 ("sudo: a password is required"), so the hook's real `sudo -n chown -R …` call genuinely fails here — a real instance of "the chown itself fails" (privilege escalation failing counts), independent of the `sudo` stub. Guarded with `@pytest.mark.skipif(sudo -n true succeeds, …)` so it self-disables rather than false-passing/false-failing on a host that DOES have real passwordless sudo for the test user (where this scenario's premise wouldn't hold).
  - `test_self_locates_two_dirs_up_from_hooks` — genuine, no override argument, no stubs: builds a synthetic `<tmp>/actions-runner-7/hooks/runner-job-started.sh` + `.../actions-runner-7/_work/`, runs the installed copy with zero args, confirms it finds its own `_work/`.
