# Frontend Foundation (Application Shell)

## Purpose

The frontend is a Next.js App Router application (TypeScript strict) that provides the **Application Shell**: the common layout, responsive navigation, base routes, and localized placeholders on which the product's functional modules are built progressively. It includes the frontend authentication session as a separate cross-cutting integration: login, ephemeral JWT handling, identity context, refresh and client-side UX guards. It contains no business authorization, RBAC or tenant-isolation enforcement; those remain backend responsibilities. Its foundation defines the architectural boundaries, cross-cutting UI conventions, and extension points every future frontend module inherits.

## Requirements

### Architecture and dependency boundaries

- THE SYSTEM SHALL use Next.js (App Router) with TypeScript in `strict` mode; a type error fails `npm run typecheck`.
- THE SYSTEM SHALL organize code into layers with a one-directional dependency rule `app → features → components / lib`, enforced by ESLint `no-restricted-imports`: `components/` and `lib/` never import `app/` or `features/`, and a feature never imports another feature's internals (only its public `@/features/<name>` entry point).
- THE SYSTEM SHALL split the shell's public surface into two doors, because a barrel is a dependency edge that ESLint does not see: `@/features/shell` is **client-safe** (`PageHeader`, the `ShellProfile` type, `useNotificationsPanel`) and `@/features/shell/server` publishes the five shells and `routeMetadata`, which reach `server-only` (`lib/theme/server`; `lib/metadata/create-route-metadata → lib/i18n/server`). Layouts and pages under `frontend/app/` import shells from the `/server` door — legal because the `no-restricted-imports` rule only governs files **under** `features/`. The split was forced by a real failure: a Client Component pulling one client hook off the general barrel dragged `server-only` into the browser bundle, `tsc --noEmit` stayed clean and the whole suite stayed green, and **only `next build` catches that class of error** (PR #136, `provenance-contract` job). A CI guard against reincidence landed right after, in PR #137.
- WHEN a future functional surface is added, THE SYSTEM SHALL provide a modular location (`features/<feature>/`) without requiring business logic in shared components.
- THE SYSTEM SHALL keep layouts, pages, and the shell chrome (shell wrappers, `ShellFrame`, `Topbar`, `Brand`, `SkipLink`, `PageHeader`, `RoutePlaceholder`) as Server Components, resolving their static text on the server via `getServerT`; `"use client"` is confined to interactive islands (active navigation, sidebar/collapse and drawer trigger backed by Zustand, bottom navigation, locale switcher, breadcrumbs/page title, overlay auto-close).
- THE SYSTEM SHALL support route-level code splitting: the navigation registry is serializable (icon names, not component imports), so future modules stay out of the shell bundle until their route is navigated.

### Application Shell and responsive navigation

- WHEN the frontend starts, THE SYSTEM SHALL render the complete Application Shell without requiring a functional backend, and resolve the request to `/` against the non-sensitive session-presence cookie in a Server Component: a present session SHALL yield a `307 Temporary Redirect` to `/dashboard`, and an absent (or non-`"1"`) session SHALL serve the public landing; the path `/` is unchanged for consumers that already point at it.
- THE SYSTEM SHALL provide five independent sibling shells selected by static route group: WorkspaceShell (`workspace`), CleanerShell (`cleaner`), TechnicianShell (`technician`), PublicShell (`public`), and GuestShell (`guest`). There is no MaintenanceShell.
- THE SYSTEM SHALL offer an optional `footer` slot on `ShellFrame`, rendered outside the `main` landmark, and SHALL reserve the mobile `BottomNavigation` height (`pb-16 md:pb-0`) on the column that wraps topbar/main/footer — not on `main` — so the footer sits above the fixed bar rather than underneath it. The four operational shells pass it; `GuestShell` does not.
- WHEN the Workspace shell is displayed, THE SYSTEM SHALL provide sidebar + topbar on desktop (≥1024px, sidebar collapsible to an icon rail), a collapsible drawer on tablet (768–1023px), and topbar + fixed bottom navigation on mobile (<768px) with at most five destinations (Dashboard, Timeline, Cleaning, Incidents, and a "More" sheet). Responsive surfaces are selected via CSS media queries, not JavaScript viewport detection — a rule that governs not only this shell's own tramos but the `Topbar` shared by all six compositions, whose narrow layout is described below and is chosen the same way.
- THE SYSTEM SHALL make CleanerShell and TechnicianShell independent and mobile-first, rendering no artificial bottom navigation or sidebar when the profile has a single navigable destination; the public slug `/tech` is preserved while the internal profile is named `technician`.
- THE SYSTEM SHALL mount a `UserMenu` (control de cierre de sesión con confirmación) en el slot `end` del `Topbar` de `WorkspaceShell`, `CleanerShell` y `TechnicianShell`, sustituyendo el default (`ThemeSwitcher` + `LocaleSwitcher`) por `[ThemeSwitcher, Separator, LocaleSwitcher, NotificationBell, UserMenu]` — la campana de notificaciones se monta en ese mismo slot, entre `LocaleSwitcher` y `UserMenu`, y su comportamiento vive en `notifications-inbox-web`; SHALL NOT montarlo en `PublicShell` (el `/login` no muestra un usuario autenticado) ni en `GuestShell` (el guest accede por token en la URL y no tiene sesión que cerrar). El comportamiento del cierre (secuencia `logout → router.replace("/") → router.refresh()`) vive en `frontend-auth-session`. Esa composición SHALL escribirse en **un solo sitio** — el Server Component `AuthenticatedTopbarActions`, que las tres shells montan— y no replicada en cada una: estuvo triplicada literalmente, que es la razón por la que el desbordamiento hubo que arreglarlo tres veces, y tenerla en un sitio es lo que hace vigilable su forma.
- WHERE el viewport sea más estrecho que el breakpoint `sm` (640 px), THE SYSTEM SHALL **reagrupar** esa composición en vez de encogerla: `ThemeSwitcher` y `LocaleSwitcher` pasan a un `Sheet` inferior desplegable desde un disparador de la propia barra, y `NotificationBell` y `UserMenu` se quedan en ella. El criterio del reparto es qué información se pierde al esconder un control tras un toque: la campana muestra **estado** (el badge de no leídas) y el `UserMenu` muestra **identidad** (quién tiene la sesión abierta en un dispositivo compartido); el tema y el idioma no muestran nada, son preferencias que se fijan una vez. El default del `Topbar` — el que reciben `PublicShell` y `GuestShell` — recibe el mismo tratamiento, y su slot `end` estrecho es solo el disparador. WHEN un control se sirva desde el desplegable, THE SYSTEM SHALL exponerlo con el mismo nombre accesible y el mismo efecto que tiene en la barra completa; el desplegable es un diálogo (`Sheet`) y no un `DropdownMenu`, porque el patrón *menu* de Radix impone `role="menuitem"` y roving tabindex sobre unos controles que son un `role="group"` de botones `aria-pressed` y un botón de acción con tooltip.
- WHEN a user opens any PRD §24 route whose module is not implemented, THE SYSTEM SHALL render a localized planned-module placeholder ("En preparación" / "In preparation") within the common visual structure, containing no business logic, API calls, invented contracts, or business mock data. The `/dashboard` and `/properties/[id]` routes are now functional surfaces (see `dashboard-web-frontend.md`); the `/properties` route is now a functional read-only surface (the paginated portfolio index, see `properties-crud.md` §«La pantalla del portfolio») on top of the existing properties API — `POST`/`PATCH` stay out of scope from the web, so creating, editing and retiring a property are exposed by future entries of their own; the `/reservations` and `/reservations/[id]` routes are now functional read-only surfaces (list + detail, see `reservations-web` archived in `changes/archive/`) on top of the existing reservations API, and both surfaces render the derived property/guest identity (`propertyInternalCode`/`propertyName`/`guestFullName`) instead of raw ids — the list's *Property* and *Guest* columns and the detail's property block, see `reservations-identity-web` archived in `changes/archive/` — `POST`/`PATCH`/`DELETE` stay out of scope from the web and are exposed by a future entry of their own; the `/incidents` and `/incidents/[id]` routes are now functional read-only surfaces (list + detail, see `incidents-web` archived in `changes/archive/`) on top of the existing maintenance API — the eleven mutation endpoints (`classify`, `triage`, `assign`, `accept`, `reject`, `en-route`, `wait-parts`, `resume`, `resolve`, `cancel` and `PATCH /incidents/{id}`) and the owner-approval response (`POST /owner-approvals/{id}/respond`) stay out of scope **from these two workspace surfaces** — the six the technician's `EXECUTE_INCIDENTS` reaches (`accept`, `reject`, `en-route`, `wait-parts`, `resume`, `resolve`) are now served from `/tech/incidents/[id]` instead (see `tech-app.md`), and the four manager operations plus the owner-approval response are exposed by future entries of their own; the `/cleaning` route is now a functional surface (list + assignment, see `cleaning-manager-view.md`) on top of the existing cleaning API — validating a finished cleaning (`POST /cleaning-tasks/{id}/validate`), the task detail, manual task creation (`POST /cleaning-tasks`) and the checklist templates stay out of scope from the web and are exposed by future entries of their own; the `/timeline` route is now a functional read-only surface (see `dashboard-web-frontend.md` §«Timeline screen») that mounts the per-property timeline over a property chosen in a selector, because the backend serves one property at a time and the global cross-property timeline of PRD §23 does not exist; the `/pricing` route is now a functional surface (see `revenue-pricing.md` §«La pantalla de precios») serving two tabs under the one exact-match descriptor — the recommendation queue with its three decision moves and on-demand regeneration, and the rules that produce it read-only — while writing a pricing rule (`POST`/`PATCH /api/v1/pricing-rules`) stays out of scope from the web and is exposed by a future entry of its own; the `/conversations` and `/conversations/[id]` routes are now functional surfaces (list + thread + manual reply, see `conversations-inbox.md`) on top of the existing messaging-ai API — creating a conversation (`POST /conversations`), escalating (`POST /escalate`) and resolving (`POST /resolve`) stay out of scope from the web and are exposed by future entries of their own; the `/tech` and `/tech/incidents/[id]` routes are now functional surfaces (assigned-incident list + the technician's cycle, photo gallery and upload, and the close form with its owner-approval gate, see `tech-app.md`) on top of the existing maintenance API; the `/cleaner` and `/cleaner/tasks/[id]` routes are now functional surfaces (the assigned-task list with status filters and per-row context, and the task detail with checklist, photo upload, incident report and the accept/reject/start/close cycle with its three-clause `409`, see `cleaner-app.md`) on top of the existing cleaning API; the remaining PRD §24 routes stay placeholders until their module ships.
- THE SYSTEM SHALL preserve access to the applicable primary destinations across desktop, tablet, and mobile layouts, driven by a single navigation registry.
- WHEN a user operates the shell by keyboard, THE SYSTEM SHALL provide a "skip to content" link, unique labelled landmarks (`header`, `nav`, `main`), a visible focus indicator, `aria-current` for the active route, `aria-expanded`/`aria-haspopup` for collapsible navigation, accessible names for icon-only controls, focus trap/return and Escape close for drawers, and ≥44×44px touch targets on bottom navigation, targeting WCAG 2.2 AA.
- WHEN any of the six `Topbar` compositions (`WorkspaceShell`, `CleanerShell`, `TechnicianShell`, the `(authenticated)` group, `PublicShell`, `GuestShell`) is rendered at a 360 px viewport, THE SYSTEM SHALL keep `document.documentElement.scrollWidth` no greater than the viewport's `clientWidth`, and SHALL hold that across the whole range from 360 px up to the `sm` breakpoint where the full layout returns — not only at the exact value of 360 px. 360 px is an ordinary phone, not an edge case, and the owner operates from one; the overflow used to live entirely in the shared header, so every authenticated surface scrolled sideways at once.
- THE SYSTEM SHALL NOT resolve that overflow by shrinking a touch surface: every touch target in the header stays at least 44×44 px in the narrow layout, including the controls served from the sheet, and `max-w-48` on the truncated `UserMenu` email is not cut below its own legibility. `NotificationBell` carries the `tap-target` utility for exactly this reason — `size="icon"` fixes a *starting* width, not a floor, so as a flex item it resolved to its 16 px min-content and measured 22 px wide the moment the `end` slot gained `min-w-0`. The `end` slot does carry `min-w-0`, like the other two, so the truncation on the email is not inert; what must not be shrinkable are the controls themselves.
- WHERE both layouts are present in the DOM at once, THE SYSTEM SHALL hide the inactive one with `display: none` (Tailwind's `hidden` / `sm:hidden`) and SHALL NOT use `invisible`, `opacity-0` or `sr-only`, so that at any width assistive technology finds exactly **one** instance of each control — no duplicated accessible name, no repeated tab stop. The three rejected utilities hide from sight only, and the difference is invisible in a code review.
- THE SYSTEM SHALL guard that overflow with an automated check that measures a **real browser** rather than jsdom, which performs no layout and reports `scrollWidth` 0, so an assertion written against the ordinary suite would measure nothing at all. A second Vitest project (`npm run test:layout`, `features/shell/components/topbar-overflow.browser.test.tsx`) renders the compositions at 360×780 in Chromium against **compiled Tailwind CSS** — without that build step the guard measures an unstyled DOM and always passes — names the offending composition and the measured width when it fails, and asserts both the root width **and** the 44×44 floor on rendered geometry, because a width-only assertion goes green over a control its parent has crushed. A structural guard (`frontend/test/topbar-overflow.test.ts`) complements it by pinning the shape rather than the widths: that no shell mounts the preference controls directly, that the wide branch is hidden with `hidden` and not with `sr-only`, and that the trigger carries `tap-target`. Both run in CI.

### Route registry

- THE SYSTEM SHALL maintain a single typed route registry (`features/shell/navigation/route-registry.ts`) covering exactly the surfaces defined in PRD §24 (26 descriptors), as the source of truth for navigation, breadcrumbs, metadata, and placeholders.
- A route descriptor SHALL carry only shell metadata (stable id, pattern, optional navigable `href`, i18n keys, serializable icon name, shell profile, match strategy, optional navigation group/order) and SHALL NOT carry permissions, endpoints, DTOs, data, counters, or business state.
- THE SYSTEM SHALL expose navigation only through per-profile selectors; there is no "all" selector, so a shell cannot render another profile's routes. Dynamic routes (`/properties/[id]`, `/cleaner/tasks/[id]`, `/tech/incidents/[id]`, `/guest/[token]`) carry no `href` and are not reachable from any menu.
- WHEN resolving the active route, THE SYSTEM SHALL match the most specific descriptor (exact, then longest valid prefix), normalizing trailing slash and ignoring query/hash; breadcrumbs are built from the descriptor's explicit key chain, never from raw path segments, and never expose IDs or tokens.

### Cross-cutting interface states

- THE SYSTEM SHALL provide reusable, accessible, mutually distinguishable conventions for loading (`aria-busy` status), error (`role="alert"`, retry only when a real reset callback is provided, never rendering raw error detail), empty (neutral, distinct from error/loading), and planned-module (`ModulePlaceholder`) states, all built on a shared `StatePanel` primitive and server-compatible.
- WHEN a nullable scalar field of the data model (`string | null`, `number | null`, or any `T | null` from a DTO) is rendered inline inside a populated row, THE SYSTEM SHALL display the em-dash `—` (U+2014) as a typographic placeholder and SHALL NOT concatenate the absent value with a sibling unit (currency code, suffix, separator) — the absence has to read as a single convention, not as a bare code or a stray space. The em-dash is a literal character in JSX, never a new i18n key (it is not language text and is the same glyph in `es` and `en`). The populated case is unchanged: the value is rendered together with its unit exactly as before. The `?? ""` operator SHALL NOT be used to coerce a DTO nullable into a render slot.
- THE SYSTEM SHALL keep the badge colour palette in exactly one place (`lib/ui/status-tone.ts`: the `Tone` union and its `TONE_BADGE_CLASS` map) and SHALL NOT let a feature restate the Tailwind classes. It was extracted from two byte-identical copies — the operational-state map in `components/property-state-badge.tsx` and the cleaning-status map in `features/cleaning/lib/task-status.ts`, whose comment still pointed at a third location the classes had already left — and the extraction was accepted only because it needed no test edited. Reusing a tone is deliberate and does not make two vocabularies one: PRD §9.1 operational-state colours and a feature's own status colours mean different things and only share the palette. The same rule now covers `features/incidents/lib/severity-tone.ts`: incident severity (`LOW`/`MEDIUM`/`HIGH`/`CRITICAL`) maps to a `Tone` next to its enum, the class strings come from `TONE_BADGE_CLASS`, and the two duplicated `SEVERITY_COLOR` tables it replaced are gone. Severity and operational state mean different things and only share the palette; the enum→tone mapping belongs to the domain, the class strings belong to `lib/ui/`.

### Internationalization (ES/EN)

- WHEN any visible string is rendered, THE SYSTEM SHALL resolve it through react-i18next keys present in both the `locales/es` and `locales/en` catalogs; no visible string is hardcoded (the only exception is the self-contained inline ES/EN catalog in `global-error.tsx`, which cannot depend on the i18n provider).
- THE SYSTEM SHALL resolve the locale per request from the non-sensitive `autohostai.locale` cookie, validated against `es | en` with `es` as the fallback, and synchronize `<html lang>`; an accessible topbar control switches ES/EN, updating i18next, the cookie, and `lang` without storing the locale in Zustand. WHEN the switch happens, THE SYSTEM SHALL re-fetchar el segmento actual del App Router (`router.refresh()`) para que los Server Components de la landing pública (`LandingView`, `Hero`, `MarketingNav`, `FeaturesGrid`, `StatsBand`, `FinalCta`, `LandingFooter` y `PublicShell`) re-ejecuten `getServerT()` con el cookie nuevo y pinten el `<main>` en el idioma destino sin recarga manual del navegador. El orden SHALL ser `i18n.changeLanguage` → escritura del cookie → `router.refresh()`, en ese orden y sin `await` ni paralelismo, para que la petición del refresh lleve la cabecera del cookie ya propagada.
- IF a translation key is missing in either locale, THEN THE SYSTEM SHALL fail an automated catalog-parity test.

### Remote state, UI state, and API access

- WHEN a future module consumes remote data, THE SYSTEM SHALL route it through TanStack Query v5 with a tenant-scoped query-key factory that requires a non-empty `tenantId` (`['tenant', tenantId, resource, ...scope]`), making global/cross-tenant keys impossible to build by accident. The shell itself declares and runs no queries.
- THE SYSTEM SHALL limit Zustand to lightweight UI state (`use-shell-ui-store.ts`: per-profile sidebar collapse preference, ephemeral overlay flags) and SHALL NOT duplicate server state; only the sidebar-preference map is persisted, under the versioned key `autohostai.ui.shell.v1`, and overlays close on navigation.
- WHEN a future module performs an HTTP request, THE SYSTEM SHALL route it through the centralized `fetch` transport (`lib/api`), which is generic (base URL + PRD §23 error envelope) and uses the generated OpenAPI `paths` types to constrain declared routes, methods, JSON request bodies and success responses. The transport never reads UI state, preserves `ApiError`/`parseApiError` for non-OK responses, exposes documented auth extension points (`getHeaders`, `onUnauthorized`) without implementing tokens, and creates no endpoint wrappers. The shell performs no backend calls and invents no endpoints, DTOs, or payloads.

### Error boundaries

- WHEN an unrecoverable failure occurs in the RootLayout or its providers, THE SYSTEM SHALL render `global-error.tsx`, which owns its document, uses a self-contained localized catalog, manages initial focus, offers a real recovery action, and never exposes `error.message`, stack traces, secrets, or internal URLs.
- WHEN content within a shell segment fails, THE SYSTEM SHALL render that segment's `error.tsx` (composing `ErrorState`) within the content slot, preserving the shell chrome, without exposing the received error and offering retry only through App Router's `reset`.
- THE SYSTEM SHALL add no `loading.tsx`, Suspense, or artificial promises to static placeholders; a future `loading.tsx` composes `LoadingState` in its owning segment.

### Metadata

- THE SYSTEM SHALL produce localized App Router metadata from the route registry keys: a default title `AutoHostAI`, a `%s | AutoHostAI` template, a localized description, and generic Open Graph. Every surface is `noindex, nofollow` except the public landing at `/`, which is the **only** indexable surface of the tree (`robots: { index: true, follow: true }`, with `metadataBase` and absolute `canonical`/`openGraph.url` derived from the public `NEXT_PUBLIC_APP_URL` allowlist entry). The indexable metadata is centralized by route name through `lib/metadata/create-route-metadata.ts` rather than scattered per page.
- WHEN metadata is generated for a dynamic route, THE SYSTEM SHALL use a generic localized label and SHALL NOT interpolate an id, token, or any `params` value (notably `/guest/[token]`); no `metadataBase`, canonical URL, or images are emitted without an authorized public URL.

### Configuration

- THE SYSTEM SHALL define a single configuration boundary (`lib/config`): `server.ts` (`server-only`) for private/runtime values, `public.ts` for an explicit allowlist of the serializable public snapshot, `runtime-config-provider.tsx` for client access, and `constants.ts` for non-sensitive defaults (locale `es`). Application code does not read `process.env` outside this boundary.
- THE SYSTEM SHALL keep `BACKEND_INTERNAL_URL` server-only and unread at shell render, expose a build-time public `NEXT_PUBLIC_APP_ENV`, and keep the feature-flag registry empty and allowlisted; no secret or non-allowlisted value reaches the browser.
- THE SYSTEM SHALL make `app/api/[...path]/route.ts` the **only** module under `app/` that reads `BACKEND_INTERNAL_URL` (through `getServerConfig()`), verified by `app/proxy-scope.test.ts`. Since `api-ingress-routing` the value does have a consumer; it still is not read at shell render. The route handler itself is specified in `ingress-https-dev` §Camino a la API.
- THE SYSTEM SHALL expose the deployed build identity through that same allowlist — `appVersion` and `buildCommitShort`, read from `NEXT_PUBLIC_*` — and nothing else about the build: the repository URL, the Pull Request number, the full commit SHA and the Actions run id never enter the snapshot, which the root layout serializes on **every** surface. See `app-version-visibility`.
- THE SYSTEM SHALL treat that allowlist as a guarantee about **values**, not only about which field names cross: `public.ts` vets the shape of the build identity and yields `""` for anything off-shape, so a widened value cannot reach the browser through a field that is itself allowlisted. This has to happen at the boundary rather than in the component that displays the value — React serializes the snapshot as a prop into the root layout's RSC payload, so an unvetted value travels in the page source of every surface no matter what any component chooses to render. See `app-version-visibility`, "El límite valida la forma de la identidad".

### Authentication integration boundary

- THE SYSTEM SHALL integrate the authentication session through `AuthProvider` between i18n and query, the API hooks `getHeaders`/`onUnauthorized`, and the static-profile route groups; the full session behavior is specified in `frontend-auth-session`.
- THE SYSTEM SHALL keep authentication tokens out of persistent browser storage and SHALL keep `BACKEND_INTERNAL_URL` server-only; the public runtime configuration may expose only the browser-facing `apiBaseUrl`.
- THE SYSTEM SHALL treat client-side guards as UX protection only. The frontend SHALL NOT implement business authorization, RBAC or tenant-isolation enforcement; the backend remains authoritative. The role allow-list on the protected shells is part of that UX layer; the same backend `403` would still reject a forged request that bypasses the routing layer.
- THE SYSTEM SHALL provide a `(authenticated)` route group with a minimal chrome (`Brand` + `UserMenu` in the `topbar` `end` slot, no `sidebar`, no `bottomNavigation`, no `footer`, no `ThemeSwitcher`, no `LocaleSwitcher`, no `PageTitle`) for the `/welcome` interstitial between login and the field-user shells (`CLEANER` and `TECHNICIAN`). The surface is described in `frontend-auth-role-routing` §«One-tap intermediate landing for field users».
- WHERE a feature hides a control by role, THE SYSTEM SHALL read it from the **deliberately partial** mirror in `lib/auth/permissions.ts` (`Permission` union + `ROLE_UI_PERMISSIONS` + `useHasPermission`), which holds only the permissions some screen actually hides on and SHALL NOT be read as the RBAC of PRD §6. Each entry SHALL be copied from `backend/app/auth/domain/policy.py` for **every** role, not from the shape of a neighbouring entry: `MANAGE_CLEANING_TASKS` gives `TENANT_OWNER: []` and `MANAGE_PRICE_RECOMMENDATIONS` grants both `TENANT_OWNER` and `PROPERTY_MANAGER`, so copying the former's shape would have hidden the owner's own decision buttons while the backend granted them. A wrong entry hides a control the backend allows, and no test outside the mirror's own catches it. WHERE a role holds the backend permission but cannot reach the screen that hides on it, THE SYSTEM SHALL still record the mirror entry as empty and SHALL name the reason: `EXECUTE_INCIDENTS` is granted by `policy.py` to `PROPERTY_MANAGER` **and** `TECHNICIAN`, yet the mirror gives `TECHNICIAN: []` because the only screen that hides on it — the dashboard card's blocked-transitions section — sits behind `READ_PROPERTIES`, which `_SELF_SERVICE` does not include; the entry becomes wrong the day a technician-reachable screen offers that action.

### Authenticated build provenance

- WHEN an authenticated workspace operator opens the provenance panel, THE SYSTEM SHALL request
  `/api/v1/provenance` through the centralized API client and show the public version plus the
  Pull Request, commit and Actions links only when the backend returns a complete provenance block.
- THE SYSTEM SHALL keep provenance in memory, fetch it only on panel open, and provide localized
  loading, error and unknown states without rendering partial links.
- THE SYSTEM SHALL keep the panel out of `RootLayout`, `PublicShell`, `GuestShell`, field shells,
  `/login` and `/guest/[token]`; private repository URL, Pull Request number, full SHA and run ID
  SHALL NOT enter the public runtime snapshot or anonymous artifacts.

### Testing and documentation

- THE SYSTEM SHALL provide a Vitest + Testing Library + jest-dom + axe test setup, colocated tests, and versioned conventions documentation (`frontend/README.md`).
- WHEN the frontend is verified, THE SYSTEM SHALL run type-check, lint, tests, and a production build without depending on a backend or fictitious business data.
- THE SYSTEM SHALL split Vitest into two projects, `node` (jsdom, what `npm test` runs) and `browser` (Chromium via Playwright, what `npm run test:layout` runs), so the ordinary suite does not drag a browser binary behind it. The browser project needs the Chromium binary installed from the lockfile (`npm exec --no -- playwright install --with-deps chromium`) — `npm exec --no --` and never `npx`, because `npx` fetches from the registry whatever the manifest asks for and that step installs system packages under the runner's passwordless sudo, on a `pull_request:` trigger the PR itself controls. Both projects run in CI, and a red layout project fails the job.

## Key files

- `frontend/app/` — RootLayout (server, providers + locale + metadata), route groups `(workspace)`/`(public)`/`(field)`/`(guest)`/`(authenticated)`, the public landing root at `page.tsx` (Server Component that resolves the anonymous/authenticated decision by reading the `autohostai.session.present` cookie and asking the backend `GET /api/v1/auth/me` when it is present — see `frontend-auth-role-routing` §«Server-side discrimination of a stale presence cookie at the application root»), `opengraph-image.tsx` (build-time OG card for the landing in `es` and `en`), six placeholder pages plus twenty functional surfaces — the public landing (`/`), the three dashboard surfaces (`/dashboard`, `/properties/[id]`, `/timeline` — see `dashboard-web-frontend.md`), the read-only properties index (`/properties` — see `properties-crud.md`), the two read-only reservations surfaces (`/reservations`, `/reservations/[id]` — see `reservations-web` archived in `changes/archive/`, with property/guest identity instead of raw ids per `reservations-identity-web` archived in `changes/archive/`), the two read-only incidents surfaces (`/incidents`, `/incidents/[id]` — see `incidents-web` archived in `changes/archive/`), the cleaning list (`/cleaning` — see `cleaning-manager-view.md`), the pricing screen (`/pricing` — see `revenue-pricing.md`), the two conversations surfaces (`/conversations`, `/conversations/[id]` — see `conversations-inbox.md`), the two technician surfaces (`/tech`, `/tech/incidents/[id]` — see `tech-app.md`), the two cleaner surfaces (`/cleaner`, `/cleaner/tasks/[id]` — see `cleaner-app.md`), the guest portal (`/guest/[token]` — see `guest-portal.md`), `/login` and the post-login interstitial `/welcome` (see `frontend-auth-role-routing`), five shell layouts, `global-error.tsx`, per-segment `error.tsx`.
- `frontend/features/shell/` — `index.ts` (client-safe door) y `server.ts` (las cinco shells + `routeMetadata`), `navigation/` (route registry, selectors, active-route matching, breadcrumbs, route metadata), `state/use-shell-ui-store.ts` y `state/use-notifications-panel.ts` (el flag efímero del panel de notificaciones, incluido en `closeOverlays()`), `components/` (five shells + chrome: `ShellFrame`, `Topbar`, `Sidebar`, `BottomNavigation`, `MoreMenu`, `NavLink`, `Breadcrumbs`, `PageTitle`, `Brand`, `SkipLink`, `LocaleSwitcher`, `TabletNavTrigger`, `OverlayAutoCloser`, `RoutePlaceholder`, `PageHeader`, `ShellFooter`, `VersionBadge`, y los tres que componen el slot `end` del `Topbar`: `AuthenticatedTopbarActions` (el único sitio donde se escribe la composición de las shells autenticadas), `TopbarPreferences` (las dos ramas responsive, Server Component) y `TopbarOverflowSheet` (la isla de cliente con el disparador y el cajón inferior)). Ninguno de los tres sale por las puertas públicas: son internos, consumidos por sus vecinos y por `app/(authenticated)/layout.tsx`.
- `frontend/components/` — `ui/` (shadcn primitives: Button, Sheet, Tooltip, Separator, Skeleton, Badge, AlertDialog, DropdownMenu), `states/` (`StatePanel`, `LoadingState`, `ErrorState`, `EmptyState`, `ModulePlaceholder`), `property-state-badge.tsx` (the single PRD §9.1 operational-state **grouping**, see `dashboard-web-frontend.md`; its Tailwind classes now come from `lib/ui/status-tone.ts`).
- `frontend/lib/` — `api/` (transport + PRD §23 errors), `auth/` (ephemeral session and refresh, plus the partial UI permission mirror, `session-presence-cookie.ts` y `clearSessionPresent()` que purga la cookie `autohostai.session.present` consumida por la raíz), `config/` (server/public/runtime boundary), `i18n/` (server/client init, locale resolution, catalogs), `query/` (client + tenant-scoped keys), `metadata/` (localized metadata builder), `ui/status-tone.ts` (the shared `Tone` palette), `utils.ts`.
- `frontend/lib/theme/use-theme-preference.ts` — hook de cliente que deriva la preferencia de tema del atributo `data-theme` de `<html>` con `useSyncExternalStore` sobre un `MutationObserver` acotado a ese atributo, sembrado por el valor del servidor en `getServerSnapshot`. Vive en `lib/` y no en `features/shell/` porque la dirección de dependencias es `app → features → components / lib` y esto es el mecanismo del tema, no la composición del shell; fichero aparte de `lib/theme/server.ts`, que es `server-only`.
- `frontend/features/auth/components/user-menu.tsx` — `UserMenu` montado en el slot `end` del `Topbar` de las tres shells autenticadas y del `(authenticated)` route group; `AlertDialog` de confirmación + `useLogoutMutation().mutateAsync() → router.replace("/") → router.refresh()` (la `useAuth().logout()` queda como envoltorio `@deprecated` para consumidores previos, sin viaje al servidor — ver `frontend-auth-session`). Texto en `locales/{es,en}/navigation.json` (`userMenu.triggerLabel`, `userMenu.logout`, `userMenu.anonymous`) y `locales/{es,en}/auth.json` (`logoutConfirmTitle`, `logoutConfirmBody`, `logoutConfirmCancel`, `logoutConfirmAction`).
- `frontend/features/auth/components/login-form.tsx` — formulario, redirección por rol vía `roleHome(user.role)` cuando no hay `?returnTo=` válido (con interstitial `/welcome?role=<rol>` para `CLEANER` y `TECHNICIAN`), y control «Volver a la landing» implementado como `<button type="button">` con `role="link"` y `aria-label` resuelto por `auth.backToLanding`, cuyo handler ejecuta `clearSessionPresent() → router.replace("/") → router.refresh()` para que la raíz sirva la landing sin red (defensa en profundidad de la interstitial; ver `frontend-auth-role-routing` §«Back-to-landing button purges the presence cookie before navigating»).
- `frontend/features/auth/lib/role-home.ts` — tabla `ROLE_HOME` (cuatro roles MVP) y helper `roleHome(role)` con default a `/dashboard`.
- `frontend/locales/{es,en}/{common,navigation,states,auth}.json` — catálogos del shell y del namespace `auth`; cada feature añade el suyo y lo registra en `frontend/lib/i18n/resources.ts` (el `import`, el array `NAMESPACES` y ambas tablas de recursos `es` y `en`).
- `frontend/{eslint.config.mjs,vitest.config.ts,tsconfig.json,components.json,test/}` — tooling and boundary enforcement.
